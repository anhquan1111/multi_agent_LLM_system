# Spec — Multi-Agent E-Commerce Support Assistant

Status: draft, frozen for the 7-day build (15/08–21/08/2026). Changes to this file require a
matching update to `AGENTS.md` and `docs/architecture.md`.

## 1. Problem

A customer-support assistant for a small online shop has to answer two fundamentally different
kinds of question, and a single RAG chain handles only the first:

- **Policy questions** — "How long do I have to return a damaged item?" — answered from prose
  documents.
- **Account questions** — "Where is order #1042 and what did it cost?" — answered from
  structured records, where a retrieval-based guess is unacceptable.

Some requests also ask the assistant to *change* something ("cancel my order"), which must never
happen on the strength of an LLM's judgement alone.

The system routes each request to the right specialist agent and gates every state-changing
action behind an explicit confirmation step.

## 2. Scope

**In scope**
- Supervisor agent that classifies a request and dispatches to exactly one specialist.
- `policy_agent` — RAG over shop policy documents, answers with citations.
- `order_agent` — read-only structured lookup over orders / products / customers.
- `action_agent` — the only component with write access (cancel order, open support ticket),
  each call paused for human confirmation before it executes.
- FastAPI HTTP interface, Dockerised, deployed to a public URL, with a single-file demo page.
- Conversation state persisted via a LangGraph SQLite checkpointer (multi-turn follow-ups work).
- A 20-question gold evaluation set measuring routing and answer correctness.

**Out of scope** (state these in the README's limitations section rather than half-building them)
- Authentication, real user accounts, multi-tenancy. `customer_id` is passed in the request body
  and trusted; this is a demo, not a shop.
- Payments, real order fulfilment, email/SMS delivery.
- Streaming token output, non-English input. The demo page is one static file, deliberately
  not a frontend project.
- Re-ranking, hybrid BM25 + dense retrieval, query rewriting — listed as future work.

## 3. Input / Output

**Input** — `POST /chat`

```json
{
  "message": "I want to cancel order 1042, is that still allowed?",
  "customer_id": "C007",
  "thread_id": "abc-123"
}
```

`thread_id` is optional; when absent the server mints one and returns it, so a client can continue
the conversation.

`route` is the supervisor's final decision, which on a multi-hop request is `finish`. `agents`
lists every specialist that actually ran, in order, which is what a client needs to show who
answered.

**Output**

```json
{
  "answer": "Order 1042 shipped on 2026-08-02. Our policy allows cancellation only before...",
  "route": "policy_agent",
  "agents": ["order_agent", "policy_agent"],
  "citations": [{"source": "returns.md", "chunk_id": "returns.md#3"}],
  "pending_action": null,
  "thread_id": "abc-123",
  "steps": 3
}
```

When the request implies a write, the graph halts and returns a `pending_action` describing what
it intends to do; the client confirms via `POST /confirm` with the `thread_id`, and only then does
the tool run. The response schema is fixed and covered by a test — it is the contract every other
piece of the system is written against.

## 4. Data

Synthetic, generated by `scripts/seed_data.py` from a fixed random seed, so the gold answers below
stay valid and the whole dataset is reproducible from source.

- **Documents** (`data/policies/*.md`) — 6 policy documents: returns, shipping, warranty, payment,
  privacy, membership tiers. Roughly 400–900 words each, deliberately containing a few
  near-duplicate passages so retrieval quality actually matters.
- **Tables** (`data/shop.db`, SQLite) — `customers` (30 rows), `products` (60), `orders` (200),
  `order_items` (500), `tickets` (initially empty; written by `action_agent`).

Real public e-commerce datasets were rejected: cleaning cost half a day and the gold evaluation
set needs answers known in advance.

## 5. Agents and permissions

| Agent | Reads | Writes | Notes |
|---|---|---|---|
| `supervisor` | routing decision only | — | hard step cap, never touches data |
| `policy_agent` | Chroma vector store | — | must cite retrieved chunks |
| `order_agent` | SQLite, whitelisted queries | — | parameterised, no free-form SQL from the LLM |
| `action_agent` | SQLite | `orders.status`, `tickets` | every call requires human confirmation |

The read/write split is structural, not a prompt instruction: read-only agents are never given the
write tools in the first place, so no amount of prompt injection reaches them.

## 6. Guardrails

- Hard cap of `MAX_AGENT_STEPS` (default 8) supervisor iterations per request.
- Stuck-loop detection: identical consecutive agent outputs terminate the run with a clear error.
- Retry with exponential backoff on transient API failures (rate limit, timeout) — not on
  validation errors.
- Tool arguments validated with Pydantic; a validation failure returns a readable error to the
  agent so it can self-correct, instead of crashing the request.
- Per-request token ceiling; the request fails loudly rather than running up cost.
- No write tool executes without an explicit confirmation turn.

## 7. Definition of done

The project is finished when all of the following are true — not when it "works on my machine":

1. A public URL answers both a policy question and an order question correctly, verified by hand
   through the live site.
2. A write request on the live URL stops for confirmation and only mutates data after `/confirm`.
3. Routing accuracy ≥ 90% (18/20) on the gold set; policy answers cite a correct source document.
4. `pytest` passes with the LLM mocked, including one integration test asserting the `/chat`
   response schema; GitHub Actions runs `ruff check` + `pytest` green on every push.
5. `docker build` produces an image that serves the API with no host dependencies beyond the
   API key.
6. README carries the problem statement, an architecture diagram, the live link, a demo GIF, local
   setup instructions, and an honest limitations / future-work section.
7. Every guardrail is covered by a test that fails if it is removed.

## 8. Tech stack

Python 3.12 · LangGraph 1.2 · langchain-core 1.5 · Gemini (`gemini-3.1-flash-lite` +
`gemini-embedding-2` truncated to 768 dims) · Chroma · SQLite · FastAPI · Docker ·
GitHub Actions · LangSmith.

Exact pinned versions live in `uv.lock`; the versions that matter to a code reviewer are repeated
in `AGENTS.md`.

## 9. Known risks

- **LangGraph 1.x vs 0.x** — most tutorials and the course material target 0.x. Import paths,
  `interrupt()`, and checkpointer setup differ. Verify against installed source, never from memory.
- **Gemini free-tier quota** — 20 calls per day per model, and a full evaluation pass costs about
  60. Mitigated by mocking every model call in tests, and by a `--routing-only` evaluation mode
  that scores the headline metric at one call per case.
- **Free hosting on ephemeral disk** — one container, and the filesystem is wiped on every deploy
  and every wake from sleep. The database and the vector index are therefore rebuilt at startup
  rather than baked into the image, which also avoids passing the API key as a build argument.
